# Automations

An automation is one TypeScript file an agent writes. It compiles into a diagram and a script, and the script runs durably. The engine lives in [`packages/automations`](../../packages/automations/src) and runs only in Signalbox Cloud on Dynamic Workflows; the compiler is [`packages/automation-compiler`](../../packages/automation-compiler/src). The cloud host and tools are in [`apps/cloud/src/automations`](../../apps/cloud/src/automations). Agents learn it from the built-in `signalbox-automations` skill in [`skill/`](../../apps/server/src/workflows/skill), which cloud runners install into their harnesses and `automation_reference` also serves.

## The engine runs on a host

The engine never touches threads, the machine or the network setup of where it runs. [`host.ts`](../../packages/automations/src/host.ts) names what it needs: threads (start, send, read, interrupt, settle, domain events, attached-run monitors), a compiler, `w.run`, a run-log sink, model options, and hooks. The cloud provides them in [`cloudEngine.ts`](../../apps/cloud/src/automations/cloudEngine.ts). The self-hosted server exposes typed Cloud-only errors and starts no automation workers. Existing local automation records remain untouched.

- **Monitors are pushed.** The engine tells the host what each thread's attached runs are (`monitorsChanged`), because a host's engine and its thread projections may live in different processes or objects.
- **Compiling needs Node.** oxc's wasm build needs threads, so a host without Node can't compile a save itself. The cloud saves what the caller compiled: a thread's machine, or the `signalbox` CLI and stdio `signalbox mcp` (operations whose reach `compiles`). It checks the shape and `AUTOMATION_COMPILED_FORMAT` before saving, so bump the format whenever the compiled output changes in a way a deployed cloud can't load. Remote `/mcp` and the app can't compile, and say so.
- **In the cloud, runs are Cloudflare Workflow instances** (#434; [`apps/cloud/src/automations`](../../apps/cloud/src/automations), [`runner/`](../../packages/automations/src/runner), [`workflow/`](../../packages/automations/src/workflow)). The engine's records still live on the user's Durable Object, but the run core is `makeHostedDriver`. Each run is one instance of the `AUTOMATION_RUNS` Workflow. Its entrypoint (`@cloudflare/dynamic-workflows`) loads the run's version as a Dynamic Worker: the version's `worker_module` beside the shared runtime. The runtime turns each step into a journaled `step.do` around `HOST.step`, then `step.sleepUntil` or `step.waitForEvent` when the step waits. Cloudflare owns the journal, replay, timers and transport retries; the object records steps for people to see and runs them with the same executors. A step that settles from outside (an answer, an agent's turn, a thread event) reaches its run through `instance.sendEvent`, typed by a hash of the step key (`eventTypeFor`). Two constraints:
  - **Loader ids are per version and runtime** (`workerIdFor`). Cloudflare bills a Dynamic Worker per id per day, and `LOADER.load` bills per call, so never load without an id or with a fresh one.
  - **Event processing still ends inside the request.** workerd ties promises to the request that made them, so every entrypoint ends with `flush`: wait for work started here, push notices, set the alarm. The alarm only starts crons; Workflows can't be created on a schedule.

  Threads and drives are other objects, and both reach automations through an outbox the receiving object dedupes by sequence. Each thread delivers its domain events to its owner's object, and attached-run monitors are pushed back to the thread. Each drive delivers its `main` and thread-branch moves ([`DriveEvents.ts`](../../apps/cloud/src/drive/DriveEvents.ts)) to everyone who could open it when it moved; the person's object turns them into `drive.changed` and `drive.branch-saved` in the drive's project, reading the changed files only when someone listens. Auto-saves and machine state never count, and a turn that saves and lands is two events, so a folder trigger doesn't fire twice per turn. Saves come compiled from the caller (see above), and built-ins ship precompiled ([`defaults/precompiled.ts`](../../packages/automations/src/defaults/precompiled.ts), regenerated by `apps/server/scripts/precompile-built-in-automations.ts`; a test fails while it's stale). Engine state must stay readable by the previous deploy for a few minutes, because a deploy reaches a live object late and may restart it on old code.

## The diagram comes from the code, strictly

[The compiler](../../packages/automation-compiler/src) parses the file with oxc and walks only what shapes the run: step calls (`w.<verb>(label, …)`), `if`/`switch`/`?:`/`&&`, loops, `try`, `Promise.all`, and local helpers (inlined once per call site). Plain code between steps is invisible. Anything that would make the diagram lie is a compile error with a fix hint, never an "unknown" node: steps inside arbitrary callbacks, the receiver passed around, a computed label. The graph is a tree ([`workflow.ts`](../../packages/contracts/src/workflow.ts)), so clients lay it out top to bottom with a recursive box layout ([`layout.ts`](../../packages/client-runtime/src/automations/layout.ts)) instead of a general graph engine.

## Runs replay; steps are journaled

Cloudflare journals each run's steps and replays its version's Dynamic Worker after a wait. The host stores step records for the run view, without replaying automation code itself. These constraints keep replays safe:

- **Step keys must be stable across replays.** The compiler injects each call site's id (`s7`) as an extra first argument. The guest runtime adds `#n` for repeat calls in the same frame, `[i]` per `each`/`repeat` iteration, `.branch` for `parallel`, and the helper's call site. `workflowNodeIdForStepKey` strips the runtime parts to find the diagram node. Changing how keys are built breaks every run in flight.
- **Code between steps must be deterministic.** The compiler rejects reading the clock or randomness outside steps ([`determinism.ts`](../../packages/automation-compiler/src/determinism.ts)); `trigger.at` is the run's deterministic start time. Runs of one version share a Dynamic Worker isolate, so the compiler emits a `load(workflow)` factory giving each run its own top-level state instead of replacing globals.
- **Cloudflare owns transport retries.** Model steps share one attempt budget within a host call across temporary pool failures and unreadable answers, with backoff that honors `Retry-After`. Recovery after a crash or the hosted transport's 15-minute timeout can restart that budget. The step timeout covers requests and backoff together.
- **Runs are pinned to the version that started them.** Saving makes a new version; running runs keep replaying their own script. A draft save stores a version without moving `version`, the live one triggers and runs use; publishing moves it.
- **A retry starts a new run.** It links to the original through `retry_of_run_id` and keeps its input and trigger. The cloud starts fresh steps for the new run; it does not inherit the original's successful step results. See [`retry.ts`](../../packages/automations/src/retry.ts).

## Steps call the host

The Dynamic Worker calls its `HOST` binding. Step executors in [`WorkflowEngine.ts`](../../packages/automations/src/WorkflowEngine.ts) do the real work:

- `agent` launches an ordinary thread; terminal `run.updated` events settle the step, and durable delivery retries missed events. `llm`, `judge` and `extract` call the models gateway on the automation owner's current folder pool. They receive only supplied text, with no thread, tools or workspace.
- `call` with `signalbox.<tool>` uses the cloud's handlers in [`cloudBuiltinTools.ts`](../../apps/cloud/src/automations/cloudBuiltinTools.ts). The automation has no calling thread and acts within its saved runtime mode.
- Calls to connected external services and `run` on the host remain unavailable. `run` can execute through the folder's GitHub Actions runner.

An automation acts with the runtime mode of the thread that saved it, so nothing may borrow more than it has: agents can't update or run an automation broader than their own thread, `w.start` can't start one broader than the caller, and `ask` steps are answered only by people through clients, never through MCP. Ending a run (cancel, failure, timeout, delete) interrupts its step fibers and agent threads with deterministic command ids and fails its open steps; cancel also cancels the runs it started.

## Runs can wait on events, bind to threads, and start over

- **`w.waitFor({ on })` with a literal `on` collects from the run's start.** The patterns come from its version's diagram, and from the run's start every matching event in its project lands in a durable inbox ([`events/runWaits.ts`](../../packages/automations/src/events/runWaits.ts)); a waiting step takes the oldest match and each event goes to one step. Steps always start waiting first and then look in the inbox, which closes the race with an event arriving mid-start. A computed `on` (the built-in "Wait for" waits on whatever its caller named) isn't in the diagram, so the listener set is rebuilt when a `waitFor` step starts waiting and that step collects only from then on; anything that must not race, like a callback, waits with a literal `on`. `w.eventCursor(label)` journals the run inbox's current sequence; passing its result as `after` to a later `w.waitFor` with a literal `on` (or a literal `watch` without `on`) skips earlier entries while preserving events that arrive after capture. Cursors carry their run id, and another run cannot use them. Waits without `after` keep the same buffering behavior.
- **`pr.*` facts are transitions over upstream's sync.** [`events/pullRequestFacts.ts`](../../packages/automations/src/events/pullRequestFacts.ts) keeps the last snapshot per thread and pull request in memory and sees every `thread.pull-request-synced`, wanted or not. After a restart the first snapshot only counts if it was synced since the process started. Comments and reviews aren't in the snapshot, but a new one moves its `updatedAt`, so `pr.commented`/`pr.reviewed` read the conversation for remarks newer than the previous `updatedAt`, only when the sync moved it and something listens. The reads go through [`PullRequestReads.ts`](../../apps/cloud/src/github/PullRequestReads.ts), registered by the cloud host.
- **Watched sources are polled once per source, and nothing registers.** A `watch` on a trigger or `w.waitFor` names an Executor list operation; its source id hashes the project, operation, args, account, list path and key, so every watcher of the same thing shares one read whatever its `fields` or `every` ([`sources/`](../../packages/automations/src/sources/sourceWatches.ts)). Each engine tick derives the watchers from the trigger index and the run-wait listeners, so saving, pausing or ending a run needs no bookkeeping. The snapshot is stored before the diff's events are enqueued: a crash in between loses that batch rather than replaying it, which is the trade the "a restart never replays" rule asks for. Projects never share a source because folders will get their own Executor connections (#293). Readers with different approval modes never share a source, so a restricted watcher can't turn a full-access automation's reads into approval prompts. Each event carries the previous read time (`since`) and a watcher started after it never gets it; someone new watching gets an immediate read as their baseline (unless the source is failing, which keeps its backoff). A pause stores who watched then, so only a new watcher (a saved or re-enabled automation, a new run) lifts it, never a restart.
- **Agents wait through built-ins, not special code.** `wait_for` runs the built-in "Wait for" attached to the caller's thread, and `watch_pull_request` runs "Watch pull request" through [`waits.ts`](../../packages/automations/src/waits.ts). The self-hosted server keeps upstream's PR watcher. Loop guards (the comment-only wake budget, giving up after failed reads) live in the built-ins' code, where people can read and change them.
- **Merging goes through a gate, not a tool.** Agents get `merge_pull_request`, which runs the built-in "Merge gate" attached to their thread. `signalbox.pull_request_action` (upstream's `PullRequestService.runAction`: merge, delete-branch, …) is a step only automations reach: the automation tool runner routes it and the MCP server never registers it ([`cloudBuiltinTools.ts`](../../apps/cloud/src/automations/cloudBuiltinTools.ts)). Since agents can save and run automations, the runner also refuses it unless the run's version is Signalbox's own or one a person published in the app (`approved_by` on the version; the app sends the draft version the person saw, and a different pending draft is refused; agents' saves and publishes count as `agent`), and only on threads of the automation's project ([`builtinTools/runner.ts`](../../packages/automations/src/builtinTools/runner.ts)). The default gate reads the pull request's evidence at one head commit (`signalbox.pull_request_read`: checks, review threads and decision, draft, conflicts, changed files), sends an unready one back to the agent, merges a ready one by itself unless a changed path or the agent's `askBecause` makes it hard to undo or undecided, and asks a person then. Those rules are plain code in [`defaults/mergeGate.ts`](../../packages/automations/src/defaults/mergeGate.ts), so a folder tightens them by customizing it. The merge names the head commit it judged: the cloud passes it to GitHub's merge API (`sha`), which refuses once anything newer landed ([`PullRequestMerges.ts`](../../apps/cloud/src/github/PullRequestMerges.ts)). This covers Signalbox's own paths; a full-access agent with a shell and the user's git credentials can still merge outside Signalbox, which only the credential broker (#74) can close.
- **Callback links use the cloud hook route.** `w.hook` makes a callback URL through [`cloudIngress.ts`](../../apps/cloud/src/automations/cloudIngress.ts); a request becomes a `hook.called` event delivered only to the run that made the link (never to triggers or other runs, since bodies can carry payment or personal data), and the link stops answering when the run ends. `wait_for({ callback: true })` picks the hook id before its run starts, so the run waits on it with a literal `on` and the tool can return the URL right away.
- **Attached runs show as thread monitors.** A run attached to a thread is a `monitor` (task id `automation-run:<automationId>:<runId>`, so clients can open it) in the thread's pending background work, so the thread stays in Working. The cloud host pushes monitor changes to the attached thread. Settle, archive and delete events cancel attached runs; Stop reaches the engine through the `automations.stopAttached` RPC the client calls when there's no turn to interrupt.
- **`w.restart` is continue-as-new.** The run succeeds with `{ restartedAs }` and a fresh run starts on the live version with the same trigger, parent, depth and attachment ([`restart.ts`](../../packages/automations/src/restart.ts)). Run links (`signalbox_automation_run_links`) record the chain; more than 30 restarts an hour fails it.
- **Built-ins are code, run through host rows.** [`defaults/`](../../packages/automations/src/defaults) holds automations Signalbox ships. Runs, steps and models are per project, so a built-in runs through a row in the project marked with its slug (`builtin_slug`, which saves never write), re-saved from the code whenever the code changes and refusing edits. Customize clears the mark, so the row becomes the project's own automation; an unmarked automation with the built-in's name always wins resolution.

## Event triggers ride the domain event stream

`{ on: … }` triggers react to orchestration-v2 domain events, which every provider adapter already produces, so one trigger works on every harness. [`automationEvents.ts`](../../packages/contracts/src/automationEvents.ts) is the one catalog: the normalizer in [`events/`](../../packages/automations/src/events) has to build each name (a test holds it to that), the compiler checks `on` against it, and the skill and clients render from it. Every domain event also passes through raw as `orchestration.<type>`, so a new upstream event is usable before anyone names it.

- **Unwanted events cost a map lookup.** Subscriptions live in an in-memory index rebuilt only after a `definition` change (save, publish, toggle, delete); a cron firing or run activity never rebuilds it or lifts a rate pause. Thread reads happen only for events someone listens to, in a worker fiber off the stream, so slow reads never delay agent steps settling.
- **The stream is a live tail.** Nothing replays after a restart; events that happened while the server was down never trigger. The dedupe key (`event:<id>` in the webhook key table, pruned after a day) covers repeats of one fact, like several terminal `run.updated` for the same turn, so ids are semantic (`turn.finished:<runId>`), not domain event ids.
- **Loops are guarded three ways.** Threads and turns automations started don't trigger by default (their message ids start with `automation:`); an automation never sees its own runs' events, and runs started by automation events count toward the `w.start` depth; past `maxRunsPerMinute` an automation's event triggers pause until it's saved or switched. The pause is in memory, so a restart lifts it.

## Webhooks run in the cloud

[`cloudIngress.ts`](../../apps/cloud/src/automations/cloudIngress.ts) validates webhook tokens, signatures, rate limits and callback ownership. [`hookStore.ts`](../../apps/cloud/src/automations/hookStore.ts) persists deliveries so the object's alarm can retry them. Webhook signing secrets stay in the cloud's hook store, separate from automation definitions. Callback payloads go only to the run that created the link.

## Observability is one wide event per run

[`runLog.ts`](../../packages/automations/src/runLog.ts) builds one wide event per run with each step's latest state. The cloud does not send these events to Workers logs because they can contain automation console output. Failures carry structured `why` and `fix` values in `errorDetail`, which clients and `automation_run_read` show.

## Persistence

Automation records live on the user's Durable Object. Tables are `signalbox_automation*` and create themselves ([`storeSchema.ts`](../../packages/automations/src/storeSchema.ts)). Keep schema changes readable by the previous deploy while objects finish upgrading.
