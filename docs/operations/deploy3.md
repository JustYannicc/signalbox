# Operate the Deploy #3 qualifier

## Provision and arm

No command here grants permission to deploy or start a provider. Deployment still requires the coordinator's separate GO. The commands below describe that future authorized operation.

1. Merge the workflow and operator source to the default branch. Configure `DEPLOY3_CONTROL_WRITER_IDS` with the actual registration, owner and CI writer IDs. The existing `cloud-production` Cloudflare account/token and the job's `github.token` are the backstop credentials. Confirm its default-branch scheduled job succeeds and can read the registered cleanup token record before allowing a consumer to use the deployment.
2. Prepare a private local plan using `Deploy3Plan` in `deploymentPlan.ts`. It binds the run ID, start UTC, exact prepared Worker entry, asset directory, compatibility settings and qualifier vars. The stage must equal the eight-character run ID. `RUN_ID` remains the qualifier UUID; it is separate from the deployment run ID. Keep Alchemy's local state and credential outputs private. No remote state Worker, evidence bucket or new host is required.
3. With the existing provisioning authority, apply `credentials.alchemy.run.ts`. Its operator token expires 45 minutes after the plan's start UTC. Supply that actual token ID in the plan and deliver its redacted value securely as `CLOUDFLARE_API_TOKEN` for `alchemy.run.ts`. Before uploading any Worker, use `operator.ts bootstrap RUN FILE` to persist the run/name/start UTC, actual `operatorTokenId`, `operatorTokenExpiresOn` and owners. The workload stack requires an exact readback of that durable record and refuses a token whose observed ID/expiry does not match. It never falls back to the provisioning credential.
4. Apply `alchemy.run.ts` without a receipt or registration. This creates the named bootstrap Worker and minute Cron. The qualifier entry must call `requireDeploy3Armed` before any native route and return 503 while unarmed. Capture the actual upload response, immutable Worker ID, bundle hash and receipt UTC. Use those values in the plan's receipt. The encoded name still gives the janitor a deadline if bootstrap is interrupted.
5. Apply the credential stack again with that receipt. It creates an `Individual Workers Admin` token scoped to the immutable Worker ID, expiring at the actual 24-hour deadline plus two hours. Capture exact namespace and Tail IDs. Create the registration JSON from those observed values and the actual owners. Register it with `operator.ts register RUN FILE`, using the authorized GitHub credential. Readback must succeed before adding that registration to the plan.
6. Supply the cleanup token as `DEPLOY3_CLEANUP_TOKEN` and apply the workload stack with `registrationJson`. It checks the durable public registration and actual token expiry before binding cleanup credentials and the receipt. It sets Cron and updates the same Alchemy Worker resource. Run `operator.ts arm-check RUN ORIGIN` afterward. This checks the actual `/deployment-ready` response, immutable Worker ID, minute schedule and cleanup token expiry without invoking a provider route. Submission of an update alone does not count as armed.

Run the Alchemy CLI from the installed workspace with the relevant entry file and `--stage RUN`; `DEPLOY3_PLAN_FILE` selects the private local plan. Credential provisioning and Worker upload use separate credentials and local stack states. Preserve both states through verified cleanup. The fixture source and prepared assets belong to the full deployment manifest, which must pin the exact qualifier entry that installs the arming guard and scheduled handler.

## Normal completion

Use `operator.ts export RUN SOURCE_FILE` to export the full evidence locally. The source file supplies `origin`, `qualifierRunId` and a fresh `directory`. The exporter copies every blob, checks source hashes and sizes, rejects unfinished journal reservations, verifies a stable complete inventory, fsyncs files and reads all local bytes back. A failure leaves the partial local directory for diagnosis and cannot release an owner. It never silently skips a large blob.

Each owner then supplies an explicit release JSON containing `runId`, `registrationSha256`, `owner`, `release: true`, `verifiedLocalExportSha256`, `sourceMessageId` and the actual `fullText`. `operator.ts release RUN RELEASE_FILE EXPORT_DIR` re-verifies the local export and binds the release to its digest. Only digests enter the public control record. The full release text and evidence stay local. `operator.ts cleanup RUN` refuses while any actual owner remains held, and can clean before the deadline after every owner releases. Resource absence and credential expiry/revocation remain separate facts; normal cleanup does not claim credential revocation.

## Written extensions and failures

Only a written coordinator extension can move the deadline. Preserve its full authority locally, update the receipt and bound runtime deadline, extend the cleanup credential's expiry to the new deadline plus two hours, and use `operator.ts extend RUN RECEIPT_FILE` to append the authority digest and replacement deadline to the registry. The immutable base registration stays unchanged; the runtime receipt carries the full written extension. Re-arm the Worker and repeat `arm-check`. The default-branch janitor uses that durable deadline, excluding registered Workers from its name-only fallback sweep. An extension is incomplete until the runtime binding and registry agree. A GitHub outage uses the last deadline bound into the Worker.

If the primary deletes itself before it can report, the janitor still enumerates the registration, checks recorded namespace IDs and token status, and posts a receipt. It keeps revisiting an absent Worker until an expired token is independently verified. A bootstrap that died before full registration remains discoverable through its preupload record. The janitor deletes it and waits until its recorded operator token is authoritatively expired before posting the final receipt. A Worker missing even that prerequisite record is cleaned by its parseable deadline, reports failure and receives no final issue receipt. Malformed identities, incomplete inventories, mismatched Worker IDs, unavailable API authority and failed receipt publication stay failures.
